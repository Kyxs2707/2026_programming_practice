## 4. 已确认的执行架构：字节码虚拟机

2026-10-19，用户在了解字节码是一种中间代码，以及 CPython、Lua、V8 等实现采用的执行路线后，明确表示“那就选择 B 吧”，确认首版采用字节码虚拟机，不先实现 AST 直接执行器作为必经阶段。

已确认的核心流程是：MYB 源码在解释器内部转换为字节码，再由 C++20 实现的虚拟机执行。用户仍直接运行 MYB 源文件，不增加手动编译、链接或先生成字节码文件的步骤。

采用该架构需要设计字节码生成、指令执行、分支与循环跳转、函数调用和源码位置映射等机制；这些具体机制按后续分项设计确认，不由执行架构选择自动确定。VM 不替代值模型、对象管理、内置能力与平台适配，也不自动保证性能目标。

语言规范中的全文件语法与结构检查仍先于用户语句执行；实际名称存在性、初始化、动态类型、参数数量及其他按执行路径检查的错误，不能因增加字节码生成阶段而擅自提前。既定求值顺序、错误即停及保留既有副作用的规则继续有效。

总体流程已按第 4.2 节确认：源码 → Lexer → Parser/AST → 全文件结构检查与函数/结构预登记 → 字节码生成 → 栈式 VM 执行。AST 用于表达程序结构、检查与生成字节码，具体模块接口仍待设计。

### 4.1 已确认采用栈式 VM

2026-10-19，用户在比较 CPython、CRuby/YARV、JVM、Lua、V8 等实现的操作数模型及取舍后，明确表示“那就使用栈式吧”，确认首版采用栈式字节码虚拟机。

这里的栈式指表达式操作数模型：典型算术指令从值栈读取操作数并将结果放回值栈。它不要求所有变量都通过临时压栈保存，也不等同于宿主 C++ 的调用栈；局部变量存放、MYB 调用帧布局、具体指令和资源限制仍须继续设计。

该选择主要考虑字节码生成和中间值管理的实现、验证成本，不预设实际性能。具体前端接入、字节码编码和对象管理也不因栈式模型获批而自动定稿。

### 4.2 已确认先构建 AST，再检查和生成字节码

2026-10-19，用户在了解 CPython、V8、PHP 与 Lua 的前端和代码生成组织后，明确表示“那就先构建 AST，再检查和生成字节码吧”，采用上一轮提出的 Flex + Bison 构建 AST、独立检查和生成字节码的方案。

已确认的阶段分工：

1. Flex 负责词法分析，Bison C++ 解析器根据文法与自定义语义动作构建 AST，保存程序结构和源码位置。
2. 检查模块基于整个文件的 AST 完成结构性声明与合法上下文检查，预登记函数和结构；此阶段不执行 MYB 用户语句。
3. 独立的字节码生成模块处理 AST 与检查所得信息，生成供栈式 VM 使用的指令和源码位置映射。
4. 全文件语法与结构检查通过后才启动 VM 执行用户语句，沿用语言规范的运行时检查和求值顺序。

上述阶段在同一解释器内部完成，不要求用户单独编译或运行额外工具。字节码生成不得因遍历整个 AST，就提前触发未执行路径上的名称存在性、初始化、动态类型或调用参数数量等运行时错误；具体字面量合法性等执行前检查仍按原语言规范处理。

AST 表示与所有权已在后续第 4.6 节确认，运行时回收路线见第 4.5 节，字节码组织见第 4.7 节；具体节点字段、生成器接口、操作码与字段宽度、局部变量与调用帧具体字段、堆与根注册接口及构建配置仍待细化；构建系统路线已由第 4.25 节确认。采用 AST 不自动批准额外的控制流图优化、JIT 或新的语言功能。

### 4.3 已确认的模块分工

2026-10-19，用户对上一轮模块划分回复“好的，我们继续讨论吧”，整体采用以下职责分组：

| 模块 | 职责 |
|---|---|
| 入口调度 | 处理命令行，组织整个运行流程，返回退出状态 |
| 源码与诊断 | 保存源码和位置，生成错误信息及 MYB 调用栈报告 |
| 前端 | 词法、语法分析，构建带源码位置的 AST |
| 结构检查 | 检查声明与合法上下文，预登记函数和结构 |
| 字节码生成 | 将 AST 转换为指令，保存指令到源码位置的映射 |
| 虚拟机 | 执行指令，维护操作数栈和函数调用状态 |
| 语言运行时 | 实现值运算、变量环境、数组、结构、内置函数和对象管理 |
| 宿主适配 | 提供文件与标准输入输出能力，集中处理平台差异 |

例如 `let values = [1, 2, 3]; print(len(values));`，由前端构建 AST，检查模块检查声明是否合法，生成器产生指令；VM 执行时使用运行时的数组、长度及输出能力，最终由宿主适配完成输出。

这些是职责分组，不预设每组仅对应一个文件或 C++ 类。运行时内部的值、环境与堆继续分别设计；各模块的数据结构、具体接口、所有权和释放时机尚未定稿。结构检查不扩展为全局静态类型分析，既有运行时检查及错误顺序保持有效。

### 4.4 已确认使用 std::variant 封装 Value

2026-10-19，用户对运行时值表示方案回复“好的，使用 A”，确认采用 `std::variant` 封装统一的 `Value`，用于变量、数组元素及 VM 操作数栈等位置。

概念上的数据表示如下，具体 C++ 类型封装与接口尚待细化：

```cpp
using ValueData = std::variant<
    NullValue, bool, std::int64_t, double,
    StringRef, ArrayRef, StructRef
>;
```

- 数字、布尔及 null 直接保存对应值。`NullValue` 是 MYB null 的宿主表示，不代表未初始化。
- `StringRef`、`ArrayRef`、`StructRef` 的类型化非拥有对象指针与 Heap 管理已按第 4.20 节确认，回收路线见第 4.5 节；具体类型字段、容器和根注册接口仍待细化。字符串保持不可变；数组和结构引用保留对象身份与共享，复制 Value 不隐式深拷贝。
- 变量重新绑定不同类型通过替换 Value 中当前保存的类别与内容实现；这不为普通变量增加固定类型约束。
- 未初始化保存在绑定或槽位的独立状态中，不能把默认 null 值当成 `let x;` 已初始化。
- 运算、转换、结构字段类型及可空检查仍由 MYB 运行时按已确认规范处理，不使用 C++ 隐式转换代替。

例如 `let x = 10; x = "hello"; let a = [1, 2]; let b = a; b[0] = 9; print(a[0]);` 中，x 的当前值类别改变，a 与 b 保持同一数组引用，按语言规则输出 9。该示例仍是设计推导，没有 MYB 解释器执行证据。

此决定选择运行时值的表示方式，与 AST 节点表示及循环对象的生命周期管理分开；后续已确认的回收路线和 AST 方案分别见第 4.5、4.6 节。函数与类型仍不是普通 MYB 数据值。

### 4.5 已确认首版采用不移动对象的标记—清除

2026-10-19，用户在比较 A（标记—清除）与 B（引用计数加循环引用回收）后，回复“首版先采用 A 吧”，确认首版采用简单、不移动对象、回收时暂停 VM 的追踪式垃圾回收。

已确认的整体规则：

- 字符串、数组和结构对象由解释器运行时堆统一管理。回收从程序仍然持有的入口引用出发，标记所有可达对象，再清除不可达对象；数组元素和结构字段中的对象引用也参与追踪。
- 不可达对象即使相互引用或引用自己，也可以回收。仍被程序持有的对象保留；普通赋值、函数传参和返回值继续共享对象，`deep_copy` 仍显式复制并保留新对象图内部的共享及循环。
- 回收期间暂停 VM 执行；存活对象不搬移。不移动不代表任意 C++ 指针都会自动保活，也不意味着对象离开局部作用域时立即释放。
- 根集合必须覆盖全局绑定、活动调用帧、操作数栈、活动遍历持有的对象等执行状态；仍在使用的字节码常量、编译阶段临时数据若含有受管对象引用，也必须纳入追踪。
- 宿主内置函数中的临时对象须显式保护，不能假定回收器会扫描 C++ 局部变量。`deep_copy` 的源对象、复制映射及尚在构造的结果等需要在可能发生回收时保持可达；具体根注册接口继续设计。
- AST 和其他宿主数据仍按各自的 C++ 所有权管理，不因运行时采用 GC 就全部交给 GC。宿主文件等资源沿用确定性清理，错误退出也必须释放，不依赖某次垃圾回收。

例如：

```myb
fn make_cycle() {
    let a = [];
    append(a, a);
}

make_cycle();
print("done");
```

按语言规则，函数返回后该数组已无法从程序活动状态访问，后续回收可以释放它的自引用环；不承诺在函数返回这一刻立即回收。这是设计推导，尚无解释器执行证据。

选择 A 的理由是用一套可达性追踪处理普通对象和循环对象，避免首版同时维护引用计数与独立的循环回收机制；代价是回收暂停和显式维护根集合。单独使用 `shared_ptr`，或将正常数组元素、字段任意改成弱引用，都不能替代这套管理方案。

对象引用的直接指针路线与 Heap 统一管理、概念负载及清理边界已按第 4.20 节确认；根枚举、稳定临时根及受控分配/增长点回收已按第 4.21 节确认；具体对象字段与堆容器、根注册 API、回收条件与阈值、分配失败策略及内存限制尚未定稿。首版不纳入分代、增量或并发回收；本决定不新增 MYB 的 `gc()` 接口。实现时应验证存活共享对象、函数返回对象、直接及间接循环、反复分配、内置函数分配期间的临时对象与错误退出；这些验证尚未执行。

### 4.6 已确认首版 AST 采用节点继承与 unique_ptr

2026-10-20，用户在比较 A（C++ 节点类继承配合 `unique_ptr` 树形所有权）、B（`std::variant` 节点配合 `unique_ptr`）及其他项目实际选择后，回复“首版就使用 A 吧”，确认采用 A 及配套所有权安排。

已确认的整体规则：

### 4.16 已确认单数组增长、独立帧记录与每帧空间预留

2026-10-21，用户对上一轮整组建议回复“好的先采用这个吧”，确认首版采用 **单个可增长 Value 数组＋独立 C++ 帧记录＋每帧预留局部区和最大求值栈空间**。这是第 4.15 节统一存储原则的具体实现选择；分块存储保留为未来可重新评估的方向，首版不同时实现两套后备存储。

字节码生成阶段为各编译执行单元记录局部槽位数量与最大操作数栈深；创建帧时在统一数组中取得对应的整段空间，逻辑上分为局部区和操作数区。父帧完整预留区域在子调用期间保留，子帧另取区域，返回后可复用释放的区域。最大栈深包括本帧尚待使用的中间值及实参，不包含子帧自身的局部和求值栈空间；不预测递归总深度，不预先分配 MYB 数组对象的全部未来元素。

帧元数据使用正常构造/销毁的 C++ 对象另存，记录代码、执行位置、区域边界、有效栈顶及诊断/清理所需状态，不与 Value 帧区打包进原始内存。具体 C++ 容器、字段名和宽度、初始化状态表、扩容倍率、数量上限及容量分析算法继续细化，不把讨论中的概念字段视为最终接口。

预留空间不建立变量绑定，也不意味着操作数已经有效；声明点、独立初始化状态及各次调用隔离不变。GC 仅追踪有效已初始化局部和当前有效操作数，并覆盖其余既定根。作用域及帧退出清除相应旧根。数组或帧容器增长后须通过索引重新取得访问位置，不能继续持有失效引用或视图；搬移 Value 不改变非移动堆对象的身份。

容量分析只是生成阶段的存储分析，不提前执行名称、初始化、动态类型、索引或运算错误检查。参数交接、进入调用的提交点、返回恢复及 VM 循环推进已由后续第 4.17 节确认；首版参数转入子帧独立区，不与父帧实参区原位重叠。具体复制/移动算法及字段仍待细化。

接受的代价：扩容可能搬移活动 Value，整帧预留可能留下暂未使用的槽位；获得的是用普通 C++ 存储组织首版、复用容量并减少自建分块管理的工作。此为工程判断，没有 MYB 性能或内存峰值实测；官方参考及此前候选比较保留在第 6.4 节。

### 4.17 已确认 VM 循环调用、参数交接与返回协议

2026-10-21，上一轮讨论明确提出方案 A 及整套参数交接与返回安排，用户回复“使用方案A吧”，确认 **VM 循环推进用户调用＋参数 Value 转入子帧独立区域＋返回统一收尾**。普通 MYB 用户调用不递归进入宿主解释函数；目标与数量检查、实参从左到右求值、参数独立绑定、对象共享、默认返回 null 及根保护均保留既定语义。

| 当轮比较 | 用户函数调用如何推进 | 与 MYB 的取舍 |
|---|---|---|
| A：VM 循环推进（已确认） | 准备新 MYB 帧后切换当前帧与指令位置，在同一个调度循环继续执行；返回时弹帧并恢复调用者 | 调用状态由 VM 明确维护，不让每层普通 MYB 调用都增加一层宿主解释器递归；需要显式实现进入/返回协议 |
| B：C++ 递归推进（未采用） | 仍维护显式 MYB 帧，但每遇用户调用再递归进入 C++ 执行函数，返回时沿 C++ 调用链回到上一层 | 控制流可对应宿主函数调用，但 MYB 递归也消耗宿主调用栈，须同时处理两层栈的限制与清理 |

已确认的配套安排：

1. 调用分为“运行时检查目标及固定数量 → 从左到右求全部实参 → 准备并进入子帧”。检查必须先于实参副作用，不能只在实参求完后的单条调用动作里才做；具体指令名称、数量和字段继续设计，不提前拒绝未执行调用。
2. 实参先保存在调用者有效操作数区；全部求值成功后，为子帧取得第 4.16 节的独立区域，将各参数的 Value 写入形参槽位并标记已初始化。首版不让子帧参数与父帧实参区重叠。标量按值保存，数组/结构 Value 仍引用原对象，不做深拷贝；具体复制或移动策略须结合 Value 引用表示与异常安全细化。
3. 子帧准备期间保留原实参根，直到参数被新的可追踪位置接管；准备成功后才提交为已进入调用并切换执行。实参中的嵌套调用失败时，外层尚未进入的目标函数不得出现在实际调用栈中。扩容前后以索引重新取得参数和帧位置，不跨增长保留旧借用。
4. 返回时先把结果放入可追踪的保护位置，再清理子帧局部、临时值、作用域和活动遍历，恢复调用者帧及其有效栈顶，最后将结果交到调用者操作数区。普通 C++ 局部 Value 不自动成为 GC 根；return; 及函数正常结束仍交回 null，错误沿既定专用异常通道传播。
5. 宿主内置继续走已确认的统一回调入口，不为 C++ 回调制造 MYB 函数帧。用户调用、返回和错误清理共用一致的帧边界约定；资源限制、具体根守卫、顶层执行记录字段和返回地址字段后续细化。

### 4.19 已确认编译后程序、独立代码单元与每单元常量表

2026-10-22，用户在比较常量归属和迁移成本后回复“那我们就先选用A吧”，确认采用 **编译后程序对象＋顶层/各函数独立代码单元＋每单元常量表** 及此前四条配套安排。编译后程序对象组织顶层代码、用户函数描述与结构定义；各代码单元保存指令、常量、源码位置映射、局部槽位数和最大操作数栈深。它与前端 AST 程序根属于不同阶段，具体 C++ 类型名未定，不把二者当作已确认的同一类型。代码单元是内部编译数据，不是 MYB 函数 Value；每次调用帧仍保存本次执行位置及动态状态，递归/重复调用共享同一份函数代码。

代码单元分开与常量表分开是不同维度：本轮比较的是具体工程组合，不声称代码分开就必须采用局部常量表。第 4.7 节“独立常量表”原指常量与指令分离，本次进一步确定为每单元表。选择 A 是维护成本判断，不是速度结论；去重算法、字符串驻留和特殊存储优化均未随此建议决定。

已确认的配套安排：

- 编译后程序对象拥有顶层代码单元、用户函数表及结构定义数据；函数描述保存名称、固定参数数量及代码单元定位信息，结构定义保存已确认字段模式。全文件检查及生成成功后再执行顶层代码；函数/结构预登记不执行函数体，也不提前建立普通顶层 let 绑定。顶层代码单元不等于隐式 main。
- 各单元内部的跳转按本单元指令编号解释；常量编号也以本单元为范围。源码定位由代码单元和指令编号共同确定，实际调用点仍由调用帧记录。具体程序/函数/单元编号、字段类型、容器及终止指令继续细化。
- 代码及元数据在生成完成后按只读数据使用，参数、局部、全局绑定值和执行位置属于运行时状态，不放进函数代码供各次调用共享。即使函数表已知名称和数量，也必须保留第 4.17 节的运行时预检，不提前拒绝未执行路径中的未知调用或参数数量错误。

按规范推导依次输出 11、21。推荐组合下，bump 的代码和常量 1 保存一份，各次调用取得独立运行状态；顶层代码及其 10/20 常量另属顶层单元，value 在执行 let 时建立全局绑定。此为设计推导，未运行 MYB。后续检查跨函数编号误用、重复/递归调用的状态隔离、未调用函数常量跨回收点保活、可变字面量身份、AST 释放后的执行诊断及运行时检查阶段。

#### 4.19.1 A/B 比较与迁移成本核对历史

2026-10-22，用户要求进一步比较 A/B、其他解释器倾向及两向更换成本。当轮仅作事实核对与工程分析，并未作出选择；用户随后按第 4.19 节确认 A。迁移资料保留为历史，集中入口及去重等额外建议不自动成为已确认接口。

A/B 都保留按顶层和函数分别组织的代码单元，区别仅在常量表的归属与常量编号范围：A 的概念访问为 current_unit.constants[i]，B 为 program.constants[i]。这些名称用于说明，不是已确认 C++ 接口。

完整例：

```myb

    return 10;
}

    return 20;
}

```

规范推导输出 30。只列相关数字常量时，A 可以是 f 的常量 0 为 10、g 的常量 0 为 20；B 可以是程序常量 0 为 10、常量 1 为 20，两函数分别引用程序表。上述编号仅为例子，不固定生成器编号顺序，程序未运行。

| 方面 | A：每单元常量表 | B：程序共享常量表 |
|---|---|---|
| 读取与调试 | 根据当前单元解释编号，查看本函数相关常量较直接 | 根据程序表解释编号，查看单元时需同时查程序表 |
| 容器及重复项 | 多个表容器，跨单元可能保存重复条目 | 集中存储，可选择跨单元去重；共享表本身不自动去重 |
| 对象与生命周期 | 多表条目仍可引用同一不可变对象；同一函数多次调用不重复创建常量表 | 集中条目也不改变对象共享规则；两种方案都须追踪程序仍持有的受管常量 |
| 执行成本 | 可按编号直接访问 | 同样可按编号直接访问；无实测不能仅凭池归属断言更快 |

“常量表条目是否共用”和“不可变字符串对象是否共用”是不同问题；即使各单元拥有各自的条目，也可令条目引用同一字符串对象。跨函数去重、字符串驻留均是额外实现选择，不能把 A 等同于重复复制全部字符串内容，也不能把 B 等同于自动节省这些内容。当前程序持有全部代码单元，不能仅凭 A/B 推断一方能更早回收未调用函数的常量。

通常不需要重写 MYB 程序、词法/语法分析、AST、局部槽位或调用帧协议；可从源文件重新生成内部指令，首版尚无磁盘字节码兼容承诺。现在仅有设计文档，改变选择成本低；实现后若常量操作集中，属于若干模块的局部重构。尚无 MYB 实现，不能可靠估计工时、行数或性能收益。

### 4.20 已确认类型化非拥有对象指针与 Heap 统一管理

2026-10-22，用户对上一轮受管对象引用与堆组织回复“使用 A 吧”，确认采用类型化非拥有对象指针及该轮整组配套安排。该决定细化第 4.4、4.5 节，继续保留非移动、暂停 VM 的标记—清除。

| 当轮比较 | Value 怎样引用受管对象 | 主要代价 |
|---|---|---|
| A：类型化非拥有对象指针（已确认） | StringRef/ArrayRef/StructRef 保存指向相应堆对象的指针，存活对象地址稳定，Heap 统一拥有并决定销毁 | 按对象地址直接访问；必须正确维护根及借用寿命，未保护的 C++ 指针不能阻止回收 |
| B：对象编号/句柄与对象表（未采用） | Value 保存对象编号或间接句柄，经表项取得对象位置；Heap 同样管理回收 | 增加间接定位、表项及复用/失效规则；可以隔离引用与实际地址，但不自动免除根保护，也不改变首版非移动回收决定 |

采用 A 是与现有非移动回收、std::variant 和首版实现成本相容的工程判断，没有性能实测。这里的“非拥有”仅指 Value 不负责用 C++ delete 释放对象；可达数组元素和结构字段仍是 MYB 对象图中的强引用，不是弱引用，也不是 C++ & 的变量别名。

已确认的配套安排：

- 堆对象分别分配，由 Heap 唯一管理销毁；可用 unique_ptr 持有各对象，但具体容器及类型层次继续细化。堆的分配登记表只用于枚举对象，不作为将所有对象保活的 GC 根。Value 及对象之间的引用不单独拥有子对象，正常复制仅复制标量或对象引用，不隐式深拷贝。
- 对象具有种类/标记等追踪所需信息。字符串对象保存不可变 UTF-8 内容；数组对象保存可增长的 Value 元素序列；结构对象关联其类型描述及字段值。具体字段、缓存和遍历状态表示继续设计；类型描述与编译后程序数据须覆盖依赖对象的使用寿命，不把它们混作 MYB 普通值。
- GC 由既定根出发，追踪数组元素及结构字段中的受管引用，统一销毁不可达对象和循环。对象析构只释放自身的 C++ 存储，不递归 delete 所引用的受管对象，不运行 MYB 回调、不抛出清理异常。有效 StringRef/ArrayRef/StructRef 不以空指针冒充 MYB null；语言 null 仍为 NullValue，未初始化仍有独立状态。
- 对象地址稳定不等于内部元素槽位稳定：数组增删或扩容可使 Value&、元素指针或借用视图失效，VM 值区和帧容器增长同样需要重新定位。宿主临时值、构造半成品、返回值及 deep_copy 映射跨回收点须显式保持可达；普通指针或 unique_ptr 登记本身不等于语言根。
- 登记到可扫描堆中的对象必须处于合法可扫描状态，构造失败不能留下悬空登记；半成品跨回收点须有根保护。根协议与允许收集的位置随后已按第 4.21 节确认；具体根注册 API、回收条件与阈值、分配失败处理、堆容器和各类字段继续另行设计。

### 4.21 已确认受控回收位置、临时根与交接保护

2026-10-22，用户对上一轮临时根与允许回收位置的整组方案回复“使用这个方案”，确认采用 A：受控分配/增长点回收，以及配套的执行根枚举、稳定 RAII 临时根和无保护空窗的交接规则。该决定落实第 4.5、4.12、4.17、4.20 节的保活责任；具体 API 和数值策略仍继续设计。

| 当轮比较 | 允许触发回收的位置 | 对 MYB 的影响 |
|---|---|---|
| A：受控分配/增长点（已确认） | 在满足回收条件时，于明确的受管对象分配或容量增长入口、实际分配/修改之前回收；这些入口可位于 VM 指令、宿主内置或编译阶段内部 | deep_copy 等复杂操作内也能回收已无用对象；必须保护跨越可能回收调用的临时值，并使执行状态与容器在回收入口处可扫描 |
| B：执行边界集中回收（未采用） | VM 只在指令之间回收，单条指令或宿主内置内部延迟；编译阶段另设阶段/代码单元边界，或明确延迟回收 | 指令内部的保活审计相对集中，但复杂内置或单个构造期间会积累分配，可能提高峰值；仍需常量根、跨边界状态和正确返回交接 |

采用 A 是针对 MYB 显式根、非移动回收及复杂内置的工程判断，没有性能或峰值实测。A 不表示每次分配都必须执行完整回收，也不是后台线程随时打断 C++。回收条件、阈值数值、容量统计精度、分配失败是否重试及内存上限继续另议；B 也不保证峰值不可接受，实际取决于单次操作的工作量。

已确认的配套安排：

- 由运行时统一枚举当前有效的执行根：全局已初始化值、各活动帧已初始化局部与有效操作数、活动遍历，以及编译后程序各单元仍持有的受管常量。预留空槽和未初始化值不追踪；未调用函数的常量不能因此漏掉。编译阶段即使尚无 VM，也要登记在生成的常量与必要临时根。
- 宿主单值临时根使用拥有自身稳定 Value 槽的 RAII 守卫；可概念性称为 RootedValue，名称和具体 API 未定。登记期间该槽不能随容器扩容或守卫移动而换址，守卫不复制/移动；注册/注销不触发 MYB GC，析构不抛异常。VM 值区及常量表通过当前容器和索引枚举，不长期登记可增长容器内元素的裸地址。
- 任何调用链只要可能抵达受控回收入口，其调用者都须先保护仍要使用的对象。操作数弹入 C++ 局部、数组移出元素得到的返回值、宿主内置参数/结果、构造半成品都不能出现无根空窗；可保留原 VM 根至接管，或先放入临时根。普通 C++ 局部、指针与 STL 容器内 Value 不会自动被追踪。
- 分配前先保护输入。新对象建立、登记到进入根槽或已受保护对象之间，要由分配/交接协议保证不再触发 GC，或直接完成受保护交接；不能把 Heap 登记误作根。跨回收点的半成品必须有根且处于合法可扫描状态。参数、用户返回与内置结果继续遵循第 4.17 节的接管顺序；具体分配及返回接口继续设计。
- 受控增长涵盖数组元素区和字符串构造存储等明显的受管负载增长，不能只统计新对象个数。入口前须保护接收对象及待写入值，使当前容器和 VM 状态一致；增长后重新按索引取得可能失效的元素位置。宿主根表或 GC 自己的工作存储操作不得递归触发 MYB GC。
- deep_copy 的源、复制映射、工作队列和尚未接入结果的复制对象均须可追踪；可以使用稳定单值根或登记的可枚举根集合，不限定逐个守卫的低效写法。具体集合接口、容器及遍历算法继续设计，不能仅保护最终结果根就忽略尚未连上的对象。
- 后续验证应能在每个允许的回收点强制收集，检查嵌套构造、循环 deep_copy、数组扩容、编译期多代码单元常量、参数/返回交接和异常退出。此为内部验证安排，不增加 MYB 的公开 gc() 内置；当前尚未实现或执行这些测试。

已确认的配套安排：

- 生成器保存编译期作用域/循环信息，确定每条正常出口退出哪些局部范围、到达哪个循环目标；这些信息本身不是 VM 的运行时作用域对象。清理撤销失效局部的有效状态与 GC 根，清除无用操作数；不销毁仍由其他绑定持有的对象，也不依赖 GC 来结束遍历限制。
- continue 清理本轮退出的局部作用域；目标为 for 时保留该次活动遍历，再进入下一轮。break 清理直到最内层目标循环之外。内层 while 的 break/continue 不能解除包围它的外层 for。每轮新建/重置相应绑定，清空或预留槽位不提前建立后续 let。
- for 先在原词法环境求来源并按规范核验，再安全登记活动遍历；登记失败不留下禁改状态。正常耗尽和 break 结束本次记录；同一数组可有多次嵌套活动遍历，结束一次不得解除其他仍活动的限制。具体计数/记录表示继续设计，不能仅用一个布尔标志覆盖所有活动遍历。
- return expr 先求完表达式并保护结果，再进入第 4.17 节统一收尾，清理本帧尚存的局部、操作数与活动遍历，然后交回结果。默认返回 null 同路处理；不在每个 return 和统一收尾重复解除同一遍历。
- 运行错误不保证经过生成的正常清理指令。沿用第 4.12 节：先保存失败位置与实际已进入的 MYB 栈，再由统一执行边界根据显式帧/活动记录清理；宿主 RAII 处理其负责的临时根与资源。每条活动记录只解除一次，清理不运行 MYB、不抛二次异常，不依赖未来一次 GC；跨多条指令的活动遍历不能只挂在单条指令的 C++ 局部守卫上。
- 顶层直接 let 仍为全局；顶层嵌套块的临时局部同样按块清理，不增加隐式 main。普通作用域退出不恢复外层对象的旧内容，已发生的外层赋值与其他副作用继续保留。
- 后续验证覆盖落出、continue、break、显式/默认 return、报错、嵌套 while/for、同数组多次活动遍历、每轮未初始化状态和返回对象保活。操作码名称、清理范围编码与共享收尾布局留待具体设计，不另改已批准的指令表示。

### 6.1 局部分开存储与统一存储的比较

当时的候选 A（推荐）：每个 MYB 调用帧拥有独立局部槽位数组，VM 共用一条操作数栈；帧记录自身操作数区的栈底，局部值及初始化状态不与表达式临时值混放。候选 B：局部槽位和操作数区都置于统一可增长值存储中，按帧划分范围并通过基址/索引访问。A 便于梳理局部状态、调用交接和 GC 根，代价是每次调用可能增加局部数组分配和实参转移；B 可减少部分分配和搬移，但区域边界、扩容及状态管理更集中。此为首版维护成本判断，不是性能实测。两者都保留第 4.8 节的编号局部槽位、动态绑定及显式 MYB 帧。

后续澄清：B 的定义是局部和临时值统一分区，不必限定为单一 vector<Value>。此前单数组图只是其一种具体实现示例；CPython 式连续帧槽位、局部/求值栈分区与分块复用也是 B 家族中的具体方向，不是与 B 并列的第三种逻辑架构。单数组或分块、帧头是否与值区打包、是否预留最大求值栈、参数是否就地复用，须分别说明，不能由“采用 B”一词自动批准。详见第 6.3 节。

操作数栈保存表达式计算中间结果，局部槽位保存本次调用的参数与局部绑定，调用帧记录当前代码、指令位置、局部存储、栈底及诊断/清理所需状态；“栈式 VM”不要求这些内容必须位于同一个物理数组。

2026-10-21，用户要求详细讨论 A/B；该轮尚未作出选择，随后已按第 4.15 节选择统一存储 B。补充比较以避免将“分开存储”简单等同于容易、“统一存储”简单等同于复杂：

- A 的常见实现是在参数求值后，将参数 Value 转入独立局部数组；B 可直接把已求完的参数区域认作新帧的前几个局部槽位，容量充足时省去这次搬移及局部数组独立分配。B 也可选择搬移，因此“统一布局必然零复制”不成立；普通局部读取等操作仍可能复制 Value。两者复制数组/结构 Value 时都只复制引用，不复制对象内容。
- A/B 都能明确记录初始化状态和枚举有效 GC 根。物理槽位可以保存合法 NullValue 作为占位，同时独立标记未初始化；MYB 读取仍须报错，并非必须使用尚未构造的 C++ 对象内存。B 可用槽位元数据或配套状态表，不因统一布局而变成静态类型系统。
- A 的固定大小局部缓冲区通常不随共享操作数栈扩容而搬移；B 的单数组实现扩容可能搬移全部活跃局部和临时值；分块实现另有取舍。两者都需防止帧容器扩容及宿主参数视图失效。[Wren 的扩容实现](https://github.com/wren-lang/wren/blob/main/src/vm/wren_value.c)会修正指入旧值区的指针；MYB 可用基址/索引减少此类修正，但仍须保证临时引用和视图有效。搬移 Value 载体不等于移动受管堆对象。
- B 返回时可以恢复统一值区的栈顶，但仍须处理 Value 销毁、初始化元数据、作用域与活动遍历，不能承诺整个返回无条件 O(1)；A 同样要清理独立局部区及本帧临时区。两者都需要保护返回值及诊断，清除过期根。
- 相同程序的参数、局部和中间值都需要保存；B 主要减少部分存储管理开销，并非少保存语言所需的值。A 可能增加小分配，B 可复用容量但一次扩容也可能搬移更大的活跃区域；容量保留、分配器及具体容器共同影响内存和速度，未做性能测量。

当时对 A 的推荐是首版分工可读性上的偏好；B 同样适合首版，不需要先实现 A 或先建设复杂优化框架。两者可通过相对局部编号与集中存储接口隔离，后续迁移仍须重验参数交接、返回、GC 与扩容，不能视作只换一个容器。以下保存当时比较及候选配套边界，不覆盖第 4.15 节的当前决定。

### 6.2 核对记录：CPython 3.14 的帧布局

2026-10-21，用户询问 CPython 在此项上的做法，该次核对时尚未选择 MYB 的 A/B；随后选择按第 4.15 节记录。以下依据固定的 CPython 3.14 分支，只描述普通 Python 函数执行所需的主要帧布局，不概括所有版本与优化调用路径。

- `_PyInterpreterFrame` 的固定帧信息之后是 `_PyStackRef localsplus` 连续槽位区；局部区包含参数、普通局部及必要的 cell/free 槽位，求值栈紧接其后。`_PyFrame_Stackbase()` 返回 localsplus 加 co_nlocalsplus，初始 stackpointer 也指向此处。可归为与 B 相近的“连续槽位内分区”，但不能说完全等于先前示意的一条全 VM vector<Value>。依据：[帧结构](https://github.com/python/cpython/blob/3.14/Include/internal/pycore_interpframe_structs.h)、[栈底与初始化接口](https://github.com/python/cpython/blob/3.14/Include/internal/pycore_interpframe.h)。
- 多数普通帧从每线程数据栈按 co_framesize 取空间，不为局部数组和求值栈分别做每调用分配。当前块不足时创建或复用新块并链接旧块，不把整个活跃调用栈当单一可增长数组搬走。依据：[PushFrame、push_chunk 与 PopFrame](https://github.com/python/cpython/blob/3.14/Python/pystate.c)。
- 统一布局不等于所有参数零搬移：`_PyEvalFramePushAndInit()` 建立新帧后调用 initialize_locals，后者把 args 中的位置参数引用交给新帧 localsplus 的对应槽位；这不是深拷贝参数对象。特殊优化调用路径须分别核对。依据：[ceval.c](https://github.com/python/cpython/blob/3.14/Python/ceval.c)。
- 官方帧设计文档明确记录：现行排列为 Specials → Locals → Stack；3.11 alpha 曾试 Locals → Specials → Stack，后者通常便于就地复用调用实参，但需额外维护局部指针，可能影响性能。该取舍说明“减少一次参数搬移”不自动保证整体更快；这是官方说明，不是本项目实测。依据：[frames.md](https://github.com/python/cpython/blob/3.14/InternalDocs/frames.md)。
- 内部执行帧与可向 Python 暴露的 PyFrameObject 分开，后者可按需创建；生成器和协程的内部帧嵌入对应对象，是每线程普通帧分配的例外。这些机制不因参考 CPython 而纳入 MYB。来源同 frames.md。

该轮只读核实 CPython 源码，并非选型批准；用户随后单独批准第 4.15 节的 B 原则。MYB 的 Value 与回收路线按既定决定，帧元数据存放及单数组或分块增长继续独立设计，不照搬 Python 的语言或对象模型。

### 6.3 B 与 CPython 式具体布局的层次比较

2026-10-21，用户要求比较“每帧连续槽位＋局部区/求值栈分区＋复用帧存储”与 B。此前把 B 的通用原则和单数组示例混在一起，容易造成并列第三方案的印象；该轮明确两者属于一般原则与具体实现组合的关系；用户随后批准 B 的一般原则，具体实现组合仍按后续讨论选择。

| 维度 | 此前单数组 B 示例 | CPython 3.14 普通帧的具体做法 |
|---|---|---|
| 局部和临时值 | 统一值区内按帧分区 | 同帧 localsplus，局部后紧接求值栈；同属统一分区思路 |
| 后备存储增长 | 单数组容量不足时可能搬移活动值 | 每线程分块数据栈，整帧装不下时取得足够大的新块，旧块中活动帧不因这次增长搬移 |
| 帧信息 | 可单独放帧表；不是 B 的硬性要求 | 固定帧头、局部区及求值栈组成连续帧区域 |
| 求值栈空间 | 可只保存当前有效深度，也可提前预留 | 编译器计算 co_stacksize，按代码需要的帧尺寸预留 |
| 复用 | 返回后保留数组容量并复用区域 | 推进/恢复数据栈顶，复用块或缓存块；复用不是独有于 CPython 的特征 |
| 参数交接 | 可设计原位参数槽位，也可搬移 | 通用路径仍把实参引用交给新帧 localsplus；零搬移不由统一分区单独保证 |

依据：[CPython 帧排列说明](https://github.com/python/cpython/blob/3.14/InternalDocs/frames.md)、[帧尺寸与栈底接口](https://github.com/python/cpython/blob/3.14/Include/internal/pycore_interpframe.h)、[最大求值栈说明](https://github.com/python/cpython/blob/3.14/InternalDocs/interpreter.md)、[分块与恢复实现](https://github.com/python/cpython/blob/3.14/Python/pystate.c)。参数路径已按第 6.2 节的 ceval.c 核实。

分块的取舍是避免普通增长时搬移旧块中的值，但仍会有新块分配、块尾空隙和管理开销；一个普通帧保持连续，不跨多个块，不同帧可在不同块中。预留最大求值栈与分块是不同维度：预留可能留下当前未使用的槽位，使帧执行在既定容量内进行；单数组也可采取预留策略。计算每函数最大操作数栈深是生成阶段的存储分析，不等于新增静态类型检查或提前触发 MYB 运行时错误。

普通块增长不搬移旧值，不代表所有借用永远有效：返回和作用域结束会使区域失效，另置的可增长帧表也可能使帧引用失效。GC 追踪当前有效值而非全部预留容量，复用时必须重置初始化与作用域状态。两种组织都须维护既定参数交接、返回值保活及诊断清理。

MYB 已选择统一分区，但仍可独立维护 C++ 帧记录，并选择单数组或分块值区；不必复制 CPython 的原始帧头打包。若将 C++ 帧头和 Value 紧密放入同一原始内存区，需额外处理对齐、对象生命周期、尺寸计算和异常清理。这些属于后续接口/存储实现的候选取舍，尚无本机性能实测，也没有因参考 CPython 获得批准。

### 6.4 单数组与分块存储、每帧预留的比较

当时第 4.15 节的 B 已确认；以下是在 B 内部提出的具体实现比较，用户随后已按第 4.16 节采用单数组增长、独立帧记录和每帧空间预留。为避免与上轮 A/B 混淆，使用“单数组增长”和“分块存储”命名。

| 候选 | 具体组织 | 主要代价 |
|---|---|---|
| 单数组增长（首版建议） | 统一值区由一个可增长的 C++ Value 数组承载，各帧占用其中一段；帧元数据另存为普通 C++ 记录，以索引定位 | 扩容时可能搬移活动 Value；不得跨增长保存旧引用，调用交接与异常清理须正确处理失效 |
| 分块存储 | 从可复用块中为每帧取得足够大的连续区域；块不足时取得新块，帧记录保存块标识及区内偏移 | 增加块选择、块尾空隙、返回时恢复及块缓存管理；普通增长不搬移旧块中的活动 Value，但返回/复用仍使旧借用失效 |

推荐单数组增长是首版维护成本判断：可用普通 C++ 容器承载 Value，先不实现分块分配器；没有实测依据表明它一定比 CPython 的做法快。两种候选都可另置 C++ 帧记录，不必把帧头和 Value 打包进原始内存。

当时的配套建议（存储/容量组织已按第 4.16 节确认，具体算法和接口继续细化）：

- 每个编译执行单元记录局部槽位数量与最大操作数栈深；创建帧时在统一值区预留本帧的局部区和求值栈容量。父帧的预留区在子调用期间保留，子帧另取区域；预留可能产生未使用空间。这只计算单帧的存储需求，不预测递归总深度，也不预先检查动态值类型、实际名称或初始化错误。
- 帧元数据另用正常构造/销毁的 C++ 记录维护代码、执行位置、区域边界、当前有效栈顶及诊断/清理状态，通过索引访问；具体字段、初始化状态表及 C++ 容器类型/宽度继续细化。即使值区不移动，帧记录容器增长也可能使引用失效。
- 只扫描有效操作数和有效已初始化局部，不扫描全部预留容量；参数求值、根交接、返回与出错遵守既定语言规则。具体参数转移算法仍待定，不由连续区域推断参数原位复用。未来从单数组改为分块须重验调用交接、根扫描、返回和异常路径，不承诺只替换容器。

实际参考：CPython 3.14 的普通帧主要从每线程分块数据栈取得空间，编译器计算 co_stacksize 后可在创建帧时预留连续求值栈；官方说明连续分配用于降低开销、改善局部性。它是分块候选的参考，其帧头打包、Python 引用表示及可见帧对象不照搬。依据：[帧说明](https://github.com/python/cpython/blob/3.14/InternalDocs/frames.md)、[求值栈说明](https://github.com/python/cpython/blob/3.14/InternalDocs/interpreter.md#the-evaluation-stack)、[分块实现](https://github.com/python/cpython/blob/3.14/Python/pystate.c)。
