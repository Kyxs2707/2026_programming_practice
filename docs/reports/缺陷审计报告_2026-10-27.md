# MYB 缺陷审计报告

本文提供已确认问题的影响、设计依据、复现命令和原始证据，供维护者确定修复顺序。日期：2026-10-27；版本：`3db7dc1e7b8cdccab6512f4d7e517b16f265b448`；分支：`codex/myb-m4`。

## 结果与范围

按根因去重后确认 3 项：2 项 P2 性能问题、1 项 P3 诊断设计偏差。本轮未确认崩溃、数据计算错误或 GC 对象失效。解释器实现保持原样。

| 编号 | 优先级 | 问题 | 实测影响 |
|---|---|---|---|
| B01 | P2 | 调用目标没有按设计建立索引，调用时反复线性查找 | 相同 30 万次 `len`，增加 5000 个未调用函数后，总耗时约 75 → 1489 ms |
| B02 | P2 | 结构构造反复进行字段集合比较和字段线性查找 | 相同 300 次构造，256 → 1024 字段，估计执行耗时约 89 → 1261 ms |
| B03 | P3 | 相对入口读取失败时没有显示已解析的绝对路径 | Debug、Release 均仅报告原始相对文件名 |

P2 表示应安排修复的性能问题；P3 表示影响错误定位的设计偏差。性能问题按输入规模和源码算法确认，不以某个固定毫秒数作为语言保证。

审计依据为[语言规范](../specs/MYB语言规范.md)、[解释器设计](../specs/MYB解释器设计.md)和已完成的 M1–M4 计划。正式开发指南、200 行应用及 Python 同功能性能报告仍是计划中的后续交付，本轮没有将它们计为解释器缺陷。

## B01：未调用函数拖慢内置及后部用户函数调用

### 触发与预期

运行大量命名调用，源文件同时声明许多未调用函数。目标可以是 `len` 等内置，也可以是位于声明表后部的用户函数。

解释器设计“字节码生成、绑定与 VM 执行”第 1 节要求执行前形成名称到用户函数/内置目标以及名称到 Schema 的只读表；第 8 节要求 PRECALL、CALL 使用同一不可变目标表。目标集合在执行期间不变化，正常调用的解析成本不应随无关函数数线性增长。

以下是生成器的最小程序形状；它会在开头分别放入 0、1000、5000 个不同名称的空函数，生成完整源文件：

```myb
let values = [1];
let i = 0;
let total = 0;
while (i < 300000) {
    total = total + len(values);
    i = i + 1;
}
print(total);
```

```powershell
python tests/audit/20261027/reproduce.py --case dispatch
```

### 实际结果

所有执行均退出 0、stderr 为空，stdout 精确为 `300000` 加 LF。

| 目标 | 未调用函数数 | 检查中位数 / ms | 总耗时中位数 / ms | 估计执行 / ms |
|---|---:|---:|---:|---:|
| `len(values)` | 0 | 16.91 | 75.41 | 58.51 |
| `len(values)` | 1000 | 19.79 | 381.67 | 361.88 |
| `len(values)` | 5000 | 35.24 | 1489.34 | 1454.10 |
| `hot()` 返回 1 | 0 | 15.82 | 81.06 | 65.24 |
| `hot()` 返回 1 | 1000 | 18.62 | 350.67 | 332.05 |
| `hot()` 返回 1 | 5000 | 30.91 | 1447.90 | 1416.98 |

仅增加声明，没有增加循环次数、实参数量或实际调用的函数体工作量。`len` 总耗时增加约 19.75 倍，检查成本只增加约 18 ms；用户函数也有同样趋势。数据处理循环会因源文件中无关函数增长而持续变慢。

### 根因、去重与修复约束

[VM::precheck](../../src/vm/vm.cpp#L65)每次顺序查找 `program_->functions`；[VM::prepare_call](../../src/vm/vm.cpp#L94)再次调用预检，然后再次查找用户函数表。内置调用需要扫描全部用户函数，后部用户函数也接近完整扫描，单次最坏成本为 O(U)，U 为用户函数数量。用户函数命中后提前结束，首个函数不会因其后增加声明而线性变慢。当前 [CompiledProgram](../../src/bytecode/program.hpp#L80)只有名称编号表，没有设计要求的调用目标表。

`hot()` 和内置变慢按这一根因合为 B01。[construction_schema](../../src/vm/vm.cpp#L41)同样逐次扫描 Schema，属于缺失只读名称解析表的同类设计遗漏，不另计一项；本表没有给出其独立计时结论。

后续应在程序执行前建立只读目标索引，运行时按编号取得目标。保留 PRECALL 在全部实参前检查目标及数量的行为；未知目标和错误参数数量仍应在实际执行路径报错。

## B02：单一结构构造的字段处理呈平方增长

### 触发与预期

仅声明一个结构，反复构造它。生成器使用固定宽度字段名 `f0000` 等，各字段均为 Int64，构造值全部为 1，按声明顺序填写。构造后只读第一个字段，累计 300 次并输出 300。

```powershell
python tests/audit/20261027/reproduce.py --case struct
```

语言规范第 7 节允许此类结构，未规定字段数的小规模限制。设计要求构造时先检查类型与完整字段集合，再按源码顺序逐字段求值和检查。已确认的字段集合及对应槽位在执行期间不变化，可以复用匹配结果。

### 实际结果

全部执行退出 0、stderr 为空，stdout 精确为 `300` 加 LF。

| 字段数 | 构造次数 | 检查中位数 / ms | 总耗时中位数 / ms | 估计执行 / ms |
|---:|---:|---:|---:|---:|
| 256 | 300 | 18.70 | 107.78 | 89.08 |
| 512 | 300 | 20.47 | 356.12 | 335.65 |
| 1024 | 300 | 19.98 | 1281.24 | 1261.26 |

字段数增加 4 倍，估计执行耗时增加约 14.16 倍；连续两次翻倍分别约为 3.77、3.76 倍。检查耗时基本稳定，源码也能直接证明平方成本。宽记录批量构造会重复支付这一成本。

### 根因、去重与修复约束

[CHECK_STRUCT](../../src/vm/vm.cpp#L327)对每个构造字段扫描声明字段，并与此前全部字段逐项检查重复。[field_slot](../../src/vm/vm.cpp#L57)每次从头扫描声明字段；CHECK_FIELD 对每个字段调用它，BUILD_STRUCT 写入时又为每个字段调用一次。每次构造重复 O(F²) 处理，F 为字段数。

本例只有一个结构，排除了 B01 中结构名称表规模的影响。字段集合检查和反复槽位查找合并为 B02，不按不同操作码拆成多个缺陷。

后续可为结构建立字段索引，并为构造方案保存字段集合检查结果及字段到槽位的映射。非法构造仍须在 CHECK_STRUCT 实际执行时失败；`--check`、未执行分支和逐字段求值顺序不得改变。字段动态值的类型检查仍须逐次执行。

## B03：入口读取错误缺少绝对路径

### 最小复现

```powershell
python tests/audit/20261027/reproduce.py --case entry --configurations debug release --output build/bug-audit-20261027/entry-both
```

脚本在独立工作目录向解释器传入不存在的相对名称 `missing source.myb`。两配置均退出 2，stdout 为空，stderr 为：

```text
myb: entry I/O error [IO]: cannot open source file: missing source.myb (OS 2)
```

解释器设计“CLI、诊断与统一边界”的命令行规则要求诊断显示按启动 cwd 解析的绝对路径。实际诊断缺少该目录，无法仅从日志判断解释器访问的是哪一个同名文件。

### 根因与去重

[WindowsHostIO::read_entry](../../src/platform/windows_io.cpp#L276)在打开文件前已通过 GetFullPathNameW 得到 `absolute`，但 catch 分支第 302 行向消息拼接的是原始 `path`。源文件不存在等入口 I/O 失败会丢失已解析目录。

[现有 CLI 测试](../../tests/cli/test_cli.py#L60)只检查文件名出现在 stderr。M3 报告中恢复入口文件名的旧修复不等于满足绝对路径契约；本项按当前剩余偏差单独记录。后续修复应保留退出码 2、无虚构行列及首错记录。
