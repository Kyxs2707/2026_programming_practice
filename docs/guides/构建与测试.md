# MYB 构建与测试

本文说明怎样直接运行 MYB、从源码构建解释器，以及执行测试和定位故障。当前实现已完成 M4 的故障边界与自动检查；语言功能见 [语言规范](../specs/MYB语言规范.md)，验收结果见 [M4 测试报告](../reports/M4测试报告.md)。

项目命令默认在仓库根目录执行。构建和测试脚本使用 PowerShell 7+；直接运行已有 EXE 可使用普通 PowerShell。

| 目的 | 操作入口 |
|---|---|
| 已有程序，运行 MYB 源文件 | 第 1 节 |
| 从源码完成构建与全量验收 | 第 2、3 节 |
| 日常修改后的增量构建 | 第 2、4 节 |
| 只运行指定测试组 | 第 2、5 节 |
| 启动、路径或工具报错 | 第 6 节 |

## 1. 直接运行与移动程序

Windows 程序目录包含以下四个文件，移动或分发时保持它们在同一目录：

```text
myb.exe
libgcc_s_seh-1.dll
libstdc++-6.dll
libwinpthread-1.dll
```

完整程序目录可在兼容的 64 位 Windows 上直接运行，用户无需安装 MSYS2 或配置开发工具 PATH。在程序目录打开终端，执行 `./myb.exe --version` 检查启动。

如果使用本仓库的 Release 构建，在仓库根目录运行：

```powershell
& ./build/release/myb.exe --version
& ./build/release/myb.exe ./examples/hello.myb
& ./build/release/myb.exe --check ./examples/hello.myb
& ./build/release/myb.exe ./examples/m1_m3_comprehensive.myb
```

`hello.myb` 输出 `3` 加换行。`--check` 完成解析、结构检查、字节码生成和核验；成功时没有输出，不执行脚本或读取程序 stdin。`--help` 显示命令用法，`--` 结束选项解析，用于传入以连字符开头的文件名。

综合示例读取一行标签，空行或 EOF 使用默认值；所有断言通过后输出 `M1-M3 ALL PASS`，报告写入 `build/m1_m3_report.txt`。报告含 CRLF 和 NUL 的读写检查内容。

脚本中的相对文件路径按启动时的工作目录解析。传入脚本的绝对路径不会切换工作目录；综合示例应从仓库根目录启动。

| MYB 退出码 | 含义 |
|---|---|
| 0 | 执行或检查成功 |
| 1 | MYB 前端、结构或运行错误，含程序内 I/O 失败 |
| 2 | 命令用法或入口文件读取失败 |
| 3 | 受控宿主资源或内部故障 |

## 2. 开发环境准备

| 工具 | 要求与来源 |
|---|---|
| PowerShell | 7+，执行构建与验收脚本 |
| C/C++ 编译器 | MSYS2 UCRT64 GCC，C++20；本机已验证 15.2.0，Ryu 使用 C99 |
| Flex / Bison | 已验证 2.6.4 / 3.8.2，位于 MSYS2 的 `usr/bin` |
| CMake / Ninja | Windows 原生 CMake 3.24+、Ninja 1.11+；生成器使用 `Ninja` |
| Python | 3.10+；构建与验收统一使用所选 UCRT64 的 Python |
| Git | CI 脚本读取提交号 |

安装好工具后，在仓库根目录设置当前 PowerShell 会话。将第一行替换为本机 MSYS2 安装位置：

```powershell
$mybMsys2Root = 'D:/msys64'
$env:PATH = "$mybMsys2Root/ucrt64/bin;$mybMsys2Root/usr/bin;$env:PATH"
$mybPython = Join-Path $mybMsys2Root 'ucrt64/bin/python.exe'
```

CI 优先使用 UCRT64 目录中的原生 CMake/Ninja，也允许从 PATH 提供它们。如果沿用本机 `build/hosttools` 的局部安装，再执行：

```powershell
$mybLocalCmakeBin = (Resolve-Path './build/hosttools/cmake/data/bin').Path
$mybLocalNinjaBin = (Resolve-Path './build/hosttools/bin').Path
$env:PATH = "$mybLocalCmakeBin;$mybLocalNinjaBin;$env:PATH"
```

需要创建这种局部安装时，可用已有带 pip 的 Python 执行以下命令，再执行上面的 PATH 设置：

```powershell
python -m pip install --disable-pip-version-check --no-deps --target build/hosttools cmake==4.1.0 ninja==1.13.0
```

这些设置只影响当前会话。CMake 配置阶段核对已有工具及仓库内固定依赖，不安装工具或联网下载源码。

## 3. 一键构建与全量验收

执行第 2 节的环境准备后，在仓库根目录运行：

```powershell
pwsh -File ./tools/ci.ps1 -Configuration Debug -Msys2Root $mybMsys2Root
pwsh -File ./tools/ci.ps1 -Configuration Release -Msys2Root $mybMsys2Root
```

每次命令会删除所选配置的 `build/debug` 或 `build/release`，然后重新配置、并行构建和测试。先退出该配置的运行中程序，并让其他终端离开该目录；需要保存的文件移到构建目录之外。日常增量编译使用第 4 节。

| 配置 | 验收内容 |
|---|---|
| Debug | 内部测试 ON；全部 C++ 内部测试、Python 驱动自测、CLI 测试、默认黑盒 |
| Release | 内部测试 OFF；编译命令无测试钩子或测试目录依赖、CLI 测试、默认黑盒 |

脚本显式选用同一 UCRT64 的 GCC 与 Python。空测试集、工具缺失、构建失败、测试失败或超时均返回非零；首个失败会终止后续步骤。

日志位于 `build/ci-logs/debug/ci.log` 和 `build/ci-logs/release/ci.log`，记录提交号、工具版本、构建及测试输出。同一配置下次运行会覆盖该日志。GitHub 的检查名为 `windows-debug`、`windows-release`；远端触发和合并要求见 [CI 与合并规则](../rules/CI与合并规则.md)。

## 4. 手动配置与增量构建

先执行第 2 节。下面一次选择一个配置；构建 Release 时将第一行改为 `'Release'`：

```powershell
$mybConfiguration = 'Debug'
$mybBuildDir = "build/$($mybConfiguration.ToLowerInvariant())"
$mybInternalTests = if ($mybConfiguration -eq 'Debug') { 'ON' } else { 'OFF' }
$mybCMake = (Get-Command cmake.exe -CommandType Application -ErrorAction Stop).Source
$mybNinja = (Get-Command ninja.exe -CommandType Application -ErrorAction Stop).Source

& $mybCMake -S . -B $mybBuildDir -G Ninja `
    "-DCMAKE_BUILD_TYPE=$mybConfiguration" `
    "-DCMAKE_C_COMPILER=$mybMsys2Root/ucrt64/bin/gcc.exe" `
    "-DCMAKE_CXX_COMPILER=$mybMsys2Root/ucrt64/bin/g++.exe" `
    "-DCMAKE_MAKE_PROGRAM=$mybNinja" `
    "-DFLEX_EXECUTABLE=$mybMsys2Root/usr/bin/flex.exe" `
    "-DBISON_EXECUTABLE=$mybMsys2Root/usr/bin/bison.exe" `
    "-DPython3_EXECUTABLE=$mybPython" `
    "-DMYB_BUILD_INTERNAL_TESTS=$mybInternalTests"
& $mybCMake --build $mybBuildDir --parallel 4
```

配置完成后，修改源码只需在同一会话执行最后一条构建命令；重新打开终端时先恢复第 2 节和本节的变量。每条命令的退出码均须为 0，可在命令结束后查看 `$LASTEXITCODE`。

| 目录或文件 | 用途 |
|---|---|
| `build/debug`、`build/release` | 分别保存两个配置的 EXE、DLL 和构建文件 |
| `build/<配置>/generated` | Flex/Bison 生成的源码及头文件 |
| `src/frontend/lexer.l`、`src/frontend/parser.y` | 扫描与文法规则的维护入口 |
| `third_party/manifest.json` | 固定 fast_float/Ryu 源码、许可及 SHA-256 清单 |

Windows GCC 构建从所选编译器所在目录检查并复制第 1 节的三个 DLL。两个可执行目标共用复制任务；增量构建也会补回缺失文件。Release 禁用 fast-math 和浮点收缩，默认关闭内部测试钩子。构建生成物留在 `build/`，不提交生成代码或二进制文件。

## 5. 分别运行测试

先完成构建，并在第 2 节设置的会话中选择实际要测的配置。每次切换 Debug/Release 都重新执行该块，避免 CLI 测试沿用上次的解释器：

```powershell
$mybTestConfiguration = 'Debug'
$env:MYB_INTERPRETER = (Resolve-Path "build/$($mybTestConfiguration.ToLowerInvariant())/myb.exe").Path
& $mybPython -m unittest discover -s tests/driver -v
& $mybPython -m unittest discover -s tests/cli -v
& $mybPython ./tools/run_blackbox.py --interpreter $env:MYB_INTERPRETER
```

Debug 内部测试还可单独运行全部用例或一个命名用例：

```powershell
& ./build/debug/myb_internal_tests.exe
& ./build/debug/myb_internal_tests.exe --case vm_iteration_failures
```

只跑一个黑盒分组时，显式选择它的 manifest：

```powershell
& $mybPython ./tools/run_blackbox.py --interpreter $env:MYB_INTERPRETER --manifest ./tests/blackbox/io/manifest.json
```

| 测试入口 | 检查范围 |
|---|---|
| [tests/internal](../../tests/internal) | C++ 模块、根保活、资源故障及清理协议 |
| [tests/driver](../../tests/driver) | 黑盒驱动自身的失败、超时及隔离行为 |
| [tests/cli](../../tests/cli) | 真实进程的参数、路径、退出码及独立目录启动 |
| [tests/blackbox/manifest.json](../../tests/blackbox/manifest.json) | 全部正式 MYB 黑盒；各子目录保留分组清单 |

黑盒为每例创建独立进程和临时工作目录，默认超时 5 秒，可逐例延长；输出及文件逐字节比较。驱动退出 0 表示全部通过，1 表示用例失败或超时，2 表示参数或 manifest 错误。失败会继续统计。预期文件独立编写，不自动改写预期或归一化实际输出；原始测试字节由 `.gitattributes` 保留。

## 6. 故障定位与验收记录

| 现象 | 检查与处理 |
|---|---|
| 启动无输出，退出码为 `0xC0000135` 或 `-1073741515` | 在运行命令后查看 `$LASTEXITCODE`；检查 EXE 旁的三个 DLL。开发者重新构建，运行用户补齐完整程序目录 |
| 综合示例显示输入提示后暂停 | 输入一行标签并按 Enter；空行使用默认值 |
| 综合示例写报告时报 I/O 错误 | 回到仓库根目录启动，确认已有 `build/`；脚本路径不会改变工作目录 |
| `Missing tool` 或 Flex/Bison/Python 未找到 | 核对 `$mybMsys2Root` 和工具表；重新执行当前会话的 PATH 设置 |
| `Missing UCRT64 runtime library` | 检查所选编译器目录中的三个 DLL，恢复该 UCRT64 安装的运行库 |
| CI 无法删除构建目录，提示文件正在使用 | 结束运行中的程序，将所有终端的当前目录移出待清理目录，再运行 CI |
| 构建路径或增量生成异常 | 执行下方构建矩阵，检查对应日志；源码与构建目录的中文加空格路径分别验收 |
| 受限环境中 MSYS 工具以 `0xC0000022` 启动失败 | 先处理工具运行权限，再重新构建；该失败发生在语言测试之前 |
| Python 创建临时目录报 `WinError 5` | 为测试会话设置可写的临时目录，使用下方命令后重跑失败测试 |

```powershell
New-Item -ItemType Directory -Force ./build/test-temp | Out-Null
$env:TEMP = (Resolve-Path './build/test-temp').Path
$env:TMP = $env:TEMP
```

当前实现和故障覆盖见 [M4 测试报告](../reports/M4测试报告.md)，早期结果见 [M2 测试报告](../reports/M2测试报告.md) 与 [M1 测试报告](../reports/测试报告_v0.1.md)。真实 Windows Terminal、传统控制台的人工验收状态单列于 [Windows 终端验收](../reports/Windows终端验收.md)。

## 7. 构建矩阵与控制台验收

完成第 2 节工具准备后，在仓库根目录执行：

```powershell
pwsh -NoProfile -File ./tools/verify_build.ps1 -Msys2Root $mybMsys2Root
& $mybPython ./tools/verify_console.py --interpreter build/m4-build/clean-debug/myb.exe --output build/m4-console-debug
& $mybPython ./tools/verify_console.py --interpreter build/m4-build/release/myb.exe --output build/m4-console-release
```

构建矩阵将手写源码、测试和固定依赖复制到 `build/m4-build/source`，执行干净并行 Debug、增量生成、关闭内部测试的 Release、中文加空格源码路径、中文加空格构建路径五组验收。增量组仅修改副本中的 `.l`、`.y`、`scanner.hpp`、`driver.hpp` 时间，检查对应生成文件或目标文件更新后恢复时间。测试失败继续记录其他组，任一组失败则总退出非零。

`build/m4-build/results.json` 保存五组结果，各组日志保存在同目录。每次默认执行会重建这些验收目录；输出目录必须位于本仓库 `build/` 内。

控制台验收器另建隐藏 Win32 控制台，在代码页 65001、936 下核对输入字节、Ctrl+Z EOF 和分块输出。它保存实际模式、代码页和结果文件；人工输入及字形显示按 [Windows 终端验收](../reports/Windows终端验收.md) 复查。
